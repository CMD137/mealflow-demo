但“能跑通”不等于“达到生产级”。本次审查发现五组必须优先处理的 P0：

1. **认证实际上可被任意验证码绕过**：登录请求的 `code` 未校验；已有手机号使用任意字符串即可登录，新手机号会自动注册。
2. **存在系统性越权和网关绕过**：顾客权限可读取全部订单、操作任意订单状态和任意支付单；商品内部库存预占列表被公开 GET 规则放行；所有业务容器端口直接暴露且控制器使用默认用户兜底。
3. **排队转订单身份写错**：队列票转单时硬编码 `userId=0`、`merchantId=10`，E2E 只验证“生成了订单”，没有验证订单归属。
4. **秒杀库存事实源错误**：Redis 模式领取成功不扣 MySQL 券库存；Redis 数据丢失后会从原始数据库库存重新初始化，形成二次放量和超发。
5. **跨服务业务缺少可闭环的补偿**：订单服务在本地事务中连续远程预占库存、锁券、申请产能、创建支付单；任一步超时或后续本地回滚都无法撤销已经成功的远程动作。排队票、库存预占和产能 token 又缺少完整超时释放任务。

招聘视角的总评是：**广度强于深度，MQ 可靠消息实现是最可信的技术亮点；安全、分布式一致性和多实例语义是当前短板。** 如果把项目原样写成“高并发、高可用、分布式事务、服务治理完善”，面试风险很高；如果诚实定义为“单机可运行的微服务化交易系统原型”，并完成第 22 节的 7 天修复，项目足以成为普通/中型公司校招简历的主项目。

### 2.2 核心业务闭环

真实存在的主链路是：

`登录 → 浏览商品 → 购物车/直接结算 → 商品快照 → 预占库存 → 锁定优惠券 → 申请产能或排队 → 创建支付单与订单 → 模拟支付 → PaymentPaid Outbox → RocketMQ → 订单确认 → 商家接单/出餐 → 释放产能并推进排队 → 取餐/送达`

服务边界按业务名词拆分，代码也基本没有直接跨服务 Mapper；然而所有服务共用同一个 MySQL 实例、同一个 `mealflow` schema 和 root 账号，服务调用又使用固定 Docker DNS 地址的 `RestTemplate`，因此当前更准确的定义是：**进程级微服务原型 + 共享数据库部署 + 手工同步编排**，不是数据库隔离、动态发现、弹性扩容的生产微服务架构。

### 2.3 业务复杂度与拆分合理性

- 订单、库存、营销、支付、排队和履约之间确实存在不同状态机，拆开后能展示一致性问题与可靠消息，具有学习和求职价值。
- 商家、购物车、认证用户单独成服务的运行收益较低，反而扩大部署、联调和权限面。以当前流量和团队规模，模块化单体会更经济。
- 建议保留“网关 + 交易订单 + 商品库存 + 营销排队 + 支付通知”5～6 个边界作为讲解模型，不要继续增加服务数量。
- Nacos 目前只有注册依赖和容器，实际调用没有通过服务发现、负载均衡或 Feign；它更像装饰性组件。应二选一：真正使用服务名和负载均衡，并验证多实例；或从简历技术栈中删除“服务治理”。

## 3. 技术栈真实性核验

| 技术 | 真实使用程度 | 是否可写简历 | 证据与限制 |
|---|---|---:|---|
| Java 17 | 核心代码使用 record、现代 Spring Boot | 是 | 但没有复杂 JVM/并发工具实践 |
| Spring Boot 3.2 / Spring 6.1 | 全服务启动、MVC、事务、调度、Actuator | 是 | 版本管理存在手工覆盖，需解释兼容性 |
| Spring Cloud Gateway | 路由、认证过滤、权限检查 | 是 | 未使用 Spring Security，授权实现有严重缺陷 |
| Nacos | 服务注册配置存在 | 谨慎 | 调用方使用固定 URL，未形成发现/负载均衡闭环 |
| MyBatis | Mapper、条件更新、状态迁移 | 是 | 无分页插件、无统一 SQL 性能验证 |
| MySQL | 所有事实表、事务、唯一索引 | 是 | 共享 schema/root，未做迁移版本化 |
| Redis | 签到 Bitmap、秒杀 Lua、排队 ZSet、产能计数 | 是 | 使用场景真实；事实源、原子性和过期治理有缺陷 |
| RocketMQ | PaymentPaid 和领域事件 Outbox、消费者记录 | 是，重点写 | 通知消费者默认关闭；不可声称所有链路都异步化 |
| Docker Compose | 18 容器一键联调 | 是 | 单节点、无持久卷、业务端口全暴露，只适合开发环境 |
| Prometheus/Grafana | Actuator 指标采集、基础面板 | 是，辅助项 | 无告警、链路追踪、SLO 或延迟分位指标 |
| Vue 3/Vite | 用户端与管理端均可构建、可联调 | 可一句带过 | 商家端主包过大，前端不是后端简历主亮点 |
| Outbox / 消费幂等 | 数据表、状态机、定时投递、恢复/重放均存在 | 是，核心亮点 | 重试无退避/上限，仍需故障注入测试 |
| 分布式事务 | 没有 Seata，也没有完整 Saga/补偿器 | 否 | 只有若干局部补偿动作，不能称完整分布式事务 |
| 高并发/高可用 | 没有可信压测数据或多实例验证 | 否 | `synchronized`、本地 ID、内存幂等均与多实例冲突 |

依赖并非“越多越好”。当前最应删除或补实的是 Nacos；不建议为了简历继续添加 Elasticsearch、Sentinel、Seata、Kubernetes。先让已有 MySQL、Redis、RocketMQ 的一致性和可测试性站得住，招聘收益更高。

根 POM 的关键版本为 Spring Boot 3.2.0、手工覆盖 Spring Framework 6.1.20、Spring Cloud 2023.0.5、Spring Cloud Alibaba 2023.0.3.4、MyBatis Starter 3.0.5、RocketMQ 5.2.0。当前完整测试能通过，说明本仓库所走路径至少可编译运行；但“旧 Boot 基线 + 单独抬高 Framework”的组合增加了 BOM 之外的兼容性验证责任。构建还出现 Javassist 依赖收集和 Commons Logging 发现冲突警告，建议通过 dependency tree 定位来源后由 BOM/排除统一，不要继续零散覆盖版本。

## 4. 核心链路审查

### 4.1 下单主链路

`OrderService.submit` 在一个本地 `@Transactional` 方法中依次调用商品快照/预占、优惠券锁定、队列产能申请，随后调用支付服务并插入本地订单与 Outbox。正常路径清楚，金额由服务端快照计算、金额以分为单位的 `int` 保存，避免浮点金额错误，这两点是好的。

主要风险：

- **P0：跨服务动作不受本地事务保护。** 库存成功后锁券失败、支付单成功后订单 insert 失败、HTTP 超时但远端实际成功，都会产生孤儿资源或重复资源。
- **P1：所有 HTTP 客户端都使用无连接/读取超时的裸 `RestTemplate`。** 一个下游卡住会长期占用订单线程和数据库连接。
- **P1：幂等只依赖 `ConcurrentHashMap`。** 重启失效、多实例不共享、无 TTL/容量限制，且没有请求指纹校验。
- **P1：支付单、订单缺少以业务请求为中心的唯一约束。** 超时重试可能创建多张支付单或多张订单。
- **P1：取消和支付确认也是“本地更新 + 多个远程调用”。** 任何中间失败都会留下部分确认状态。

推荐最小闭环：建立 `order_submit_request(request_id,user_id,request_hash,status,order_id,last_error)` 持久幂等表；每个资源预占都带全局业务键；订单保存明确的 Saga 步骤；失败/超时任务按状态执行反向补偿；所有远程调用配置超时且只对幂等操作有限重试。

### 4.2 排队与排队转单链路

队列采用 MySQL 保存票与 token 事实、Redis ZSet 保存等待热索引，并能从 MySQL 重建 Redis；数据库提交后再调整 Redis 计数并定时校准，这个方向是合理且适合面试讲解的。

严重问题是 `OrderService.createOrderFromTicket` 获取票后，创建订单时硬编码 `userId=0L`、`merchantId=10L`。这会让真实排队用户生成的订单归属错误。现有 E2E 只检查新订单存在和状态，没有断言用户、商家、金额与原票一致，因此测试绿灯掩盖了 P0。

此外，Redis 的 `ZRANGE` 与 `ZREM` 是两个命令；多个队列实例可能同时取到同一票。产能“读取 held 数量 → 判断 limit → 插入 token”也只靠单 JVM `synchronized`，多实例会超发 token。等待票/HELD token 过期缺少完整扫描和对库存、优惠券的补偿。

### 4.3 秒杀领券链路

Lua 脚本把“检查库存、检查用户是否领取、扣 Redis 库存、写用户集合”放在 Redis 单次原子执行，能避免单 Redis 实例上的超卖和一人多领，是实质性亮点。

但 Redis 成功后只写 `user_voucher`，没有同步扣减 MySQL `voucher.stock`。当 Redis key 丢失或重建时，脚本会再次使用数据库原始库存初始化，造成二次发券。补偿逻辑的 `INCR` 和 `SREM` 也不是一个 Lua 原子操作。券的开始/结束时间字段未进入领取条件，管理员直接修改库存还会覆盖已经消费的数量。

建议让 MySQL 保存“总库存/已发数量”事实，Redis 只保存可用令牌；领取结果通过异步落库或同步条件更新形成可校验账本，重建时用 `总库存 - 成功发放数 - 在途数`，而不是原始库存。补偿也使用 Lua 一次完成并记录唯一业务事件。

### 4.4 支付与可靠消息链路

支付服务在本地事务中把支付单置为成功并写 `PaymentPaid` Outbox；定时任务以 NEW/FAILED → SENDING → SENT 状态投递 RocketMQ；订单消费者使用数据库 `consumer_record` 的 `(event_key, consumer_group)` 唯一键和 PROCESSING/SUCCESS/FAILED 状态实现至少一次消费下的去重、超时恢复与重放。这是整个项目最值得写简历和重点准备面试的部分。

它仍有四个边界要诚实说明：

- 生产者发送成功但来不及标 SENT 会重复发送，这是 Outbox 的正常语义，依赖消费者幂等兜底。
- 当前 FAILED 每 5 秒无限重试，没有指数退避、最大次数、`next_retry_time` 和人工死信流程。
- MQ 客户端没有显式检查发送状态，也缺少超时/批量/背压参数说明。
- 订单消费后继续同步确认库存和优惠券；下游部分成功时，消息重投并不能自动恢复所有业务步骤。

### 4.5 履约与通知链路

接单、出餐、取餐、送达状态齐全；出餐会释放产能并推进下一张排队票，业务闭环有一定复杂度。但履约服务先远程更新订单/队列，再写本地操作记录和 Outbox，本地回滚无法撤销远程状态；排队转单 HTTP 返回值未检查业务 `success`，失败后票可能停在 PROCESSING，且没有恢复任务。

通知支持模板、多渠道投递记录、SSE、消费记录和重放，代码并非空壳。不过 `docker-compose.yml` 明确设置 `NOTIFY_EVENT_CONSUMER_ENABLED=false`，默认完整环境不会消费订单/履约领域事件。因此简历只能写“实现通知事件消费能力”，不能写“默认链路已由 MQ 自动通知用户”，除非启用后补 E2E 证据。

## 5. Java 代码质量审查

### 做得好的部分

- 包结构总体按 controller/service/mapper/api 或能力子包划分，record DTO 降低样板代码。
- 金额使用整数分，状态更新多数使用条件 SQL，减少丢失更新。
- `PersistentConsumerRecordTemplate`、Outbox 客户端、MQ 封装形成了可复用基础设施，而不是每个服务复制一套。
- 关键事务通过 `afterCommitOrNow` 延后调整 Redis 派生计数，体现了本地事务边界意识。
- Mapper 大多显式列名，没有发现大面积 `SELECT *`。

### 问题清单

| 级别 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P1 | `IdGenerator` 从 `MAX(id)` 初始化后用本地 `AtomicLong` | 多实例生成重复主键 | 数据库自增、号段或雪花算法，并做时钟/实例位测试 |
| P1 | `IdempotentTemplate` 为无界本地 Map | 重启失效、多实例失效、内存增长 | 持久请求表 + 唯一键 + 请求哈希 + 结果快照 |
| P1 | 仅 promotion 有统一异常处理，其他服务异常响应不一致 | 业务异常可能表现为 500，前端和重试难判断 | 在 common/infra 提供统一 Advice 与错误契约 |
| P2 | 多个服务用 `synchronized` 保护业务临界区 | 仅保护单 JVM，容易制造“已并发安全”错觉 | 让数据库条件更新/唯一键或 Redis Lua 承担原子性 |
| P2 | Service 类过长且同时负责编排、状态机、HTTP、序列化 | 单测困难，失败策略散落 | 拆为领域服务、端口适配器、Saga/应用服务 |
| P2 | 运行时 `PostConstruct` 查询元数据并 ALTER TABLE | 多实例启动竞争、要求 DDL 权限、不可审计 | Flyway/Liquibase 版本迁移 |
| P2 | 默认身份值散落在多个 Controller | 掩盖认证缺失并造成直连越权 | 业务服务只接受网关签名身份或内部凭证，缺失即拒绝 |
| P3 | 部分命名把 demo 行为包装为通用能力 | 面试解释容易失真 | 用 `MockPayment`、`DemoAuth` 明确边界 |

Java 基础层面没有明显低级语法问题，但在并发语义上要特别准备：`synchronized`、`ConcurrentHashMap` 与 `AtomicLong` 只在单进程成立，不能据此声称分布式幂等或全局唯一。

## 6. 数据库设计与 SQL 审查

### 优点

- 库存使用 `UPDATE ... SET stock=stock-qty WHERE stock>=qty`，比先查后扣更可靠。
- 订单、支付、履约状态转换多使用当前状态作为 WHERE 条件，具备乐观状态机特征。
- `consumer_record(event_key,consumer_group)`、库存预占请求等关键表有部分唯一约束。
- 金额以分保存；核心业务时间、状态、业务编号都有落库。

### 主要问题

| 级别 | 问题 | 直接后果 |
|---|---|---|
| P1 | 所有服务共享一个 schema 和 root 凭证 | 无法独立授权/迁移，误操作影响全系统；微服务数据边界较弱 |
| P1 | 无 Flyway/Liquibase，仅 `schema.sql always` + 运行时 ALTER | 版本不可追踪，升级和回滚不可重复验证 |
| P1 | `payment_order` 缺少 `order_id`/业务请求唯一键，订单缺少必要唯一业务约束 | 网络重试或重启后重复创建 |
| P1 | 预占/票/token 有过期时间却缺少完整到期索引、扫描和补偿闭环 | 长期占库存、占券、占产能 |
| P2 | 管理端列表普遍不分页 | 数据增长后拖慢数据库和网络，可造成内存压力 |
| P2 | 订单后台按 `merchant_id + create_time/status` 查询缺少匹配复合索引 | 大表扫描/排序风险 |
| P2 | Outbox 常按 `status ORDER BY id LIMIT` 拉取，仅状态单列索引 | 可改为 `(status,id)`，并以 EXPLAIN/基准验证 |
| P2 | 若干请求 ID 唯一性未包含用户/商家/业务类型或没有请求指纹 | 不同请求碰撞时返回旧结果或复用错误资源 |
| P3 | 无 CHECK 约束保证数量、金额、库存非负 | 只能依赖应用校验，运维/脚本可写入非法值 |

没有外键在微服务场景可以接受，但前提是每个服务有清楚的数据所有权和对账/修复能力；当前共享 schema 且缺少对账任务，使“无外键”的风险被放大。

SQL 性能上最明显的 N+1/多次往返包括：商品快照和预占逐项查写、队列列表先取 ID 再逐票查询并获取 Redis rank、签到月历逐日 GETBIT。先做分页和批量查询，再用真实数据量执行 EXPLAIN；不要在没有基准的情况下堆索引。

## 7. Redis 审查

| 使用点 | 评价 | 风险 |
|---|---|---|
| 签到 Bitmap | 场景匹配，空间效率好 | 置位与积分 INCR 非原子；Redis 丢失即丢历史；月历 31 次往返；无生命周期 |
| 秒杀 Lua | 原子检查/扣减/一人一领，是真亮点 | MySQL 库存未同步；重建可二次放量；补偿非原子；未检查活动时间 |
| 等待队列 ZSet | 排序与 rank 场景匹配，MySQL 可重建 | poll 非原子；重建使用 `KEYS`；多实例可能重复推进 |
| 产能 inflight 计数 | 作为派生缓存并支持校准，方向合理 | 判断容量和创建 token 非原子；Redis 故障时本地 fallback 各实例分裂 |

Redis 不是装饰性使用，但必须明确哪些是事实、哪些是派生数据。建议的原则是：订单、券发放、排队票、产能 token 以 MySQL 事实表和唯一约束为准；Redis 负责热点判断、排名和快速拒绝；任何 Redis 数据都应能从事实表无歧义重建。禁止用 `KEYS prefix*` 做线上重建，改为版本化 key 空间、SCAN 或直接切换新版本前缀。

签到奖励至少用 Lua 把 `GETBIT/SETBIT/INCR` 合并，并把积分流水落 MySQL；连续签到可一次 GET 整段位图后本地计算。秒杀补偿应使用 Lua 原子执行“恢复库存 + 移除用户”，并通过唯一事件记录保证只补一次。

## 8. RocketMQ 与异步设计审查

### 真实能力

- 支付事务与 Outbox 写入处于同一 MySQL 本地事务。
- 定时投递存在抢占状态、失败状态、卡在 SENDING 的恢复逻辑。
- RocketMQ 消息携带 event key/type 等属性。
- 消费者以数据库唯一键和状态机实现去重，保存 payload，支持恢复和人工重放。
- Prometheus 暴露 Outbox/消费记录数量，管理端可观察和操作部分记录。

### 不足

- Outbox 无最大重试、指数退避、下一次重试时间与最终失败告警，毒消息会高频永久重试。
- 消费端异常会让整个批次重投；虽有业务去重，但吞吐和故障定位仍受影响。
- `send()` 结果未显式校验 `SendStatus`，生产者和消费者参数基本使用默认值。
- 没有 Testcontainers/真实 Broker 自动化用例验证“发送成功后数据库更新前崩溃”“重复投递”“消费业务成功后 ack 前崩溃”。
- 领域事件中只有 PaymentPaid → Order 是默认 E2E 的关键异步链；通知消费者在 Compose 关闭，不能把所有 Outbox 都包装成已落地的削峰架构。

这里使用 MQ 的合理原因是支付结果和订单确认不应由支付 HTTP 请求强耦合，且可靠重试与重复投递是客观需求；但普通下单仍是同步串行流程，所以“MQ 削峰下单”不成立。面试时应主动说清：**当前 MQ 解决可靠事件传递和解耦，不是已验证的大流量削峰系统。**

## 9. 微服务与服务治理审查

### 当前真实形态

- 网关承担外部入口，但 Docker 同时将 8101～8110 等业务端口发布到宿主机。
- 服务向 Nacos 注册，但调用地址来自固定配置/Docker 服务名，未使用注册发现、客户端负载均衡或熔断。
- 全部服务使用同一 MySQL schema/root 用户；逻辑表虽分域，物理权限未隔离。
- Redis、RocketMQ、Nacos、MySQL 均为单节点，没有副本、故障切换和持久卷。
- Compose 对业务服务多为 `service_started`，没有完善 healthcheck 和就绪依赖。

因此不能声称：服务治理完善、支持弹性扩容、高可用部署、数据库按服务隔离。可以声称：完成了微服务进程拆分、统一网关、容器化联调，并实际暴露和处理了跨服务一致性问题。

### 边界建议

以求职 ROI 而言，不必物理拆库和上 Kubernetes。先做到：只暴露网关；业务服务验证内部调用凭证；实际使用或删除 Nacos；为订单/库存/营销/支付定义数据所有者；用契约测试固定接口；用两实例验证 ID、幂等、队列和秒杀语义。这个“两实例证明”比再加三个中间件更能体现架构能力。

## 10. 分布式事务、幂等与一致性

### 一致性模型判定

项目目前是“本地事务 + 同步调用 + 若干补偿接口 + 部分 Outbox”，尚未形成完整 Saga。`@Transactional` 只覆盖当前服务的数据源，不能回滚远程 HTTP 或 RocketMQ 动作。尤其是订单创建和履约推进，把远程副作用放在本地事务内部会拉长事务，并产生经典的超时不确定性。

### 按风险排序

1. **P0：下单预占资源无法保证最终释放。** 缺少持久 Saga 步骤和统一超时补偿扫描。
2. **P0：秒杀 Redis/MySQL 库存没有单一事实口径。** Redis 丢失可直接超发。
3. **P0：排队转单写错身份。** 这是确定性数据错误，不是理论边界。
4. **P1：内存幂等和本地 ID 在多实例失效。** 一旦扩容就可能重复订单/支付或主键冲突。
5. **P1：消息消费只保证事件级去重，消费内部多个远程步骤仍可能部分完成。** 应将消费处理拆成可重入状态机。
6. **P1：补偿动作本身缺少幂等事实和原子性。** 例如 Redis 库存恢复与用户集合删除分两步。

### 推荐模型

不建议为了简历直接引入 Seata。对本项目最合适的是显式 Saga/流程状态表：每次提交生成全局 `submit_request_id`，记录 `STOCK_RESERVED → VOUCHER_LOCKED → CAPACITY_HELD → PAYMENT_CREATED → ORDER_CREATED`；每一步使用同一业务键和唯一约束，重复调用返回同一结果；失败或超时按相反顺序补偿；补偿状态同样落库且可重试。这样既易解释，也能用集成测试故障注入证明。

## 11. 安全性审查

这是当前最薄弱、也最容易让面试直接失分的部分。

### P0 证据

| 问题 | 静态证据 | 运行验证 | 后果 |
|---|---|---|---|
| 验证码未校验 | `AuthUserService.login` 不读取/比较 `code` | 已有用户以 `anything` 登录成功 | 任意账号接管 |
| 顾客可读取全部订单 | 网关将 `/orders/**` 统一映射为 `ORDER_WRITE`，顾客拥有此权限；订单列表/详情无归属校验 | 顾客 Token 成功读取 `/orders/admin`，得到 52 条订单 | 批量隐私泄露、IDOR |
| 顾客可改任意订单状态 | `pay-success/cancel/merchant-accept/meal-ready/...` 都位于同一权限前缀 | 从路由矩阵可直接推出 | 绕过支付、跨角色推进履约 |
| 商品内部预占信息公开 | 任何 `/catalog/**` GET 被视为公开，包括 `/catalog/internal/stocks/reservations` | 无 Token 成功读取，得到 61 条预占 | 泄露用户、订单、库存业务数据 |
| 服务直连绕过网关 | Compose 发布所有服务端口；Controller 缺身份时使用 demo 默认值 | 直连用户服务无 Token 返回默认用户 100 | 网关认证形同可绕过 |
| 商家/履约无资源归属校验 | 只检查权限名，不比较 `X-Merchant-Id` 与路径/订单商家 | 代码确认 | A 商家员工可操作 B 商家资源 |
| 支付 IDOR | 顾客具有 `PAYMENT_WRITE`，支付详情和 mock-pay 不校验订单用户 | 代码确认 | 查看/支付任意支付单 |

值得肯定的是，网关会移除外部伪造的 `X-User-Id/X-Merchant-Id` 等身份头，并在 Token 校验后重新注入；内部路径也优先按内部权限拦截，实测顾客调用内部队列接口被拒绝。但这些局部正确性无法抵消上述路由和部署层面的绕过。

### 其他风险

- Token 为 7 天 UUID，明文存数据库，无登出/吊销/刷新/过期清理；数据库泄露即会话泄露。
- 登录无频率限制、失败次数、验证码过期/一次性使用或设备风险控制。
- CORS 在过滤器和 YAML 两处维护且允许源不一致，商家端和用户端配置可能漂移。
- 图片只信任声明 MIME 和大小，未校验魔数/内容，也无恶意文件扫描。
- Nacos 认证关闭，Redis 无密码，Grafana 使用演示凭据；可接受于本地，但必须与生产口径隔离。
- 未发现仓库中提交的真实云 AK/SK；Compose 内密码均为公开 demo 配置。

### 最小修复顺序

1. 明确 demo 登录：开发环境使用一次性验证码表/Redis code，生产 profile 必须真实校验；禁止任意 code。
2. 把权限从“URL 前缀粗分类”改为“角色能力 + 资源归属”：用户只能访问自己的订单/支付/票/通知，商家只能访问绑定 merchant。
3. 公共路由使用精确白名单，不得用 `/catalog/` 全前缀；`internal` 路由优先且需服务凭证。
4. Compose 只发布网关、前端和必要运维端口；服务间请求使用不可伪造的内部凭证或 mTLS（求职版先做 HMAC/共享内部 Token 即可）。
5. 去掉所有默认身份兜底，缺少可信身份立即返回 401/403。
6. 增加 MockMvc/WebTestClient 权限矩阵测试，至少覆盖匿名/顾客/本商家/他商家/内部服务五类主体。

## 12. 性能、并发与稳定性

### 当前不能成立的性能声明

仓库里的 `load-seckill.ps1` 和 `load-peak-orders.ps1` 更接近并发演示：分别启动有限任务并统计返回状态，没有固定压测机模型、预热、吞吐、P50/P95/P99、错误率、资源曲线，也没有验证“成功数不超过库存/一人一单/账实一致”。因此不能声称 1 万 QPS、性能提升百分比、高并发稳定或 MQ 削峰效果。

### 性能热点

| 级别 | 热点 | 原因与建议 |
|---|---|---|
| P1 | 远程调用无超时 | 线程与连接池可能被无限占用；配置 connect/read timeout、隔离池和有限重试 |
| P1 | 多实例临界区靠 `synchronized` | 扩容后无效；用 SQL 条件更新、唯一键或 Lua |
| P2 | 后台/内部列表不分页 | 数据量增长后全表结果进入 JVM；加入游标/分页和最大 page size |
| P2 | 队列列表 N+1 | 批量查票，排名按需/分页获取 |
| P2 | 商品逐项远程/数据库处理 | 批量快照、批量预占或限定购物车上限 |
| P2 | Redis `KEYS` 重建 | 大 keyspace 阻塞；SCAN/版本前缀切换 |
| P2 | 签到月历逐日 GETBIT | 一次读取位图后本地计算 |
| P2 | 商家端 JS 约 1.24 MB | 路由分包已有但 Element Plus/依赖仍大；按需引入与 bundle 分析 |
| P2 | Outbox 毒事件固定频率重试 | 指数退避、最大次数、告警和人工重放 |

### 稳定性判断

单实例开发环境能够稳定跑通 E2E；但没有证明多实例、网络分区、Redis 重启、RocketMQ 重复消息、MySQL 主从切换等场景。MySQL/Redis/RocketMQ 未挂持久卷，容器重建会丢状态；服务也没有系统化优雅停机、就绪检查、熔断降级和容量保护。正确表述是“完成本地全链路可运行性”，不是“达到高可用”。

### 已完成

- Maven 聚合构建，默认 14 模块可一次测试通过。
- 10 个主要业务服务都有至少一个持久化测试，总计 33 个测试。
- 两个前端可构建；Compose 可启动完整依赖与服务；冒烟脚本覆盖从登录到履约、排队转单。
- Actuator/Prometheus、Grafana、Outbox/消费记录等业务指标存在。
- 文档数量和领域覆盖明显高于普通课程项目，接口、事件、状态、迁移、E2E 都有记录。

### 缺口

| 级别 | 缺口 | 招聘影响 |
|---|---|---|
| P1 | 无 CI 配置 | 无法证明每次提交自动回归 |
| P1 | 无权限/越权测试 | P0 安全问题长期未被发现 |
| P1 | 无真实 Redis/RocketMQ/MySQL 并发与故障集成测试 | 核心技术亮点缺乏证据，测试绿灯仅代表单进程 happy path |
| P1 | E2E 未断言排队转单用户/商家/金额 | 确定性 P0 被冒烟遗漏 |
| P2 | 无前端自动化测试 | 两套 UI 的关键流程只能手工回归 |
| P2 | 无版本化数据库迁移 | schema 演进风险高 |
| P2 | 无统一 trace ID/MDC/跨服务传播 | 故障时很难还原一次下单 |
| P2 | 指标无告警、SLO、延迟分位 | “可观测”停留在看图，不形成运营闭环 |
| P2 | 无 OpenAPI/契约测试 | 服务接口漂移依赖人工发现 |

现有单测很多是 Spring Context + H2 的持久化 happy path，价值高于纯 mock，但 H2 MySQL mode 不能替代真实 MySQL 的锁、隔离级别、唯一键竞争和 SQL 兼容测试。建议引入 Testcontainers，优先写 8～12 个高价值测试，而不是追求覆盖率数字：重复下单、多实例 ID、并发领券、队列同票竞争、支付消息重复、消费者崩溃恢复、资源归属矩阵、Saga 超时补偿。

## 14. 真正成立的项目亮点

1. **Payment Outbox + RocketMQ + 持久消费记录。** 有事务写事件、抢占投递、卡死恢复、事件唯一键、消费者状态机、重放和监控，是完整度最高的工程链路。
2. **数据库条件扣库存与预占状态机。** 使用条件 UPDATE 避免单库并发下的先查后扣超卖，预占/确认/释放有明确状态。
3. **MySQL 事实 + Redis 派生队列索引。** 等待票落库、Redis ZSet 排名、启动/定时重建体现了缓存可恢复思想，虽然并发细节仍需修。
4. **Redis Lua 实现秒杀原子入口。** 单 Redis 上库存和一人一领检查原子，适合用于解释 Lua 的边界；必须同时披露数据库事实源缺陷。
5. **从用户端到商家端的交易/履约业务闭环。** 不只是后端接口，还能在 Compose 中跑普通下单、排队、支付事件和履约。
6. **可观察的可靠性运维入口。** Outbox/消费者记录/补偿任务可查、可恢复/重放，并有 Prometheus 指标，体现了“出错后如何运营”的意识。
7. **文档与交付意识。** 模块、事件、状态码、测试报告、迁移计划和一键脚本比较齐全，适合校招现场快速展示。

这些亮点的共同特点是“源码和运行结果都能证明”。它们比“用了多少中间件”更值得放在项目描述第一屏。

## 15. 主要短板与技术债

### 必须优先修（P0/P1）

- 真实验证码/会话边界、精确路由白名单、订单/支付/商家/履约资源归属。
- 排队转单必须使用票内真实 user/merchant，并补全 E2E 断言。
- 持久幂等、全局 ID、订单/支付业务唯一键，至少经两实例并发测试。
- Redis 秒杀库存与 MySQL 账本统一，补偿 Lua 原子化。
- 订单 Saga/补偿步骤、票/token/库存/券超时清理，远程调用超时与失败状态。

### 随后修（P2）

- Flyway、CI、统一异常、trace ID、分页、批量查询、索引 EXPLAIN。
- Outbox 重试退避/上限/告警，真实 Broker 故障集成测试。
- 只暴露网关，持久化容器数据，增加业务健康检查。
- 启用并测试通知消费者，或收缩对通知异步链路的表述。

### 不建议当前做

- 为了“高级”引入 Seata、Elasticsearch、Kubernetes、服务网格。
- 在没有压测和火焰图前做 JVM 参数调优或复杂缓存层。
- 继续拆分更多微服务、物理分库或引入多种 MQ。
- 用 Redisson 分布式锁包住所有方法；优先数据约束和可重入状态机。

## 17. 面试高风险点

以下问题如果答成“已经解决”会被代码反证：

1. **你们如何校验验证码？** 当前没有校验。必须承认 demo 边界并展示修复。
2. **为什么 `@Transactional` 能保证库存、优惠券、支付一致？** 它不能跨 HTTP；只能保证订单库本地事务。
3. **你如何保证接口幂等？** 本地 Map 只适合单实例演示，不是分布式幂等。
4. **为什么 ID 不重复？** 当前 `MAX + AtomicLong` 在多实例会冲突。
5. **Redis 丢数据后秒杀库存怎么恢复？** 当前从数据库原始库存恢复会超发，这是必须修的问题。
6. **队列如何避免两个实例取同一票？** 当前 `ZRANGE + ZREM` 非原子，不能避免。
7. **顾客为什么不能操作别人的订单？** 当前事实上可以，权限名和资源归属是两层不同问题。
8. **Nacos 解决了什么？** 当前只注册，没有用于调用和负载均衡。
9. **MQ 是否削峰下单？** 没有；下单同步，MQ 主要承载支付结果可靠事件。
10. **消息会不会丢/重复？** Outbox 降低丢失，至少一次必然允许重复，消费者记录去重；业务步骤仍需可重入。
11. **压测多少 QPS？** 当前没有可信数据，不能编数字。
12. **为什么十个服务不是过度设计？** 应承认求职/学习目的，并给出生产环境更小的边界方案。
13. **容器删掉会怎样？** 当前无持久卷，数据库、Redis、MQ 数据可能丢失。
14. **你的测试为什么没发现硬编码用户？** 因为 E2E 断言只覆盖存在性/状态，没有验证业务不变量。
15. **通知是否真的消费订单事件？** 代码支持，但默认 Compose 关闭消费者。

最好的面试策略不是辩解，而是用“现状 → 失败场景 → 根因 → 已修/最小修复 → 测试证据”五步回答。主动暴露边界通常比被面试官从源码中抓出更加分。

## 24. 最终结论：现在够不够开始投递？

**可以开始投递，但不建议把当前未修版本直接作为冲刺大厂的主打项目。**

更精确的判断是：

- 对一般实习、小型公司和传统软件岗，当前业务完整度已经足够获得面试机会；应立即并行投递，不要等项目“完美”。
- 对中型互联网 Java 后端岗，至少先完成 7 天计划中的认证/越权、排队转单、秒杀库存和持久幂等四项，否则源码深挖风险过高。
- 对大厂核心交易/高并发岗位，除了上述修复，还需要真实并发/故障测试、压测数据，以及扎实的算法、Java、JVM、MySQL、Redis、网络与操作系统基础；项目本身无法替代这些门槛。

最终招聘标签应是：**“有完整交易系统实践、对可靠消息有真实实现、正在把 demo 级微服务原型收敛为可验证一致性系统的应届候选人”**，而不是“已经做出生产级高并发微服务平台”。前一个标签真实、有成长性，也更容易在面试中守住；后一个标签会引来当前代码无法承受的追问。

建议从今天开始按两条线并行：每天固定投递和基础题训练，同时用前 7 天只解决会让数据错、权限穿透和简历失真的问题。完成后，以 Outbox/消费幂等为主亮点，以“发现并修复分布式边界”为第二亮点，这会比再堆任何新中间件更有说服力。
